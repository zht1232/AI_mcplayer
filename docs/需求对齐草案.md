# MC AI 伙伴需求对齐草案

更新日期：2026-10-04。用户已确认开始构建；当前实现纯客户端模组，并进行隔离客户端/服务器测试。尚未进行用户正式服务器的插件兼容性实测。

## 已确认需求

- 加入现有 Minecraft 26.2 服务器；原交付资料描述该服务器为 Paper，实际核心与构建号需在接入时核对。
- 产品目标是能自主独立干活的生存队友，行为要足够像人。
- 具有较强自主性：没有直接指令时，也能自己找事做、补资源、种田、推进生存；遵守主人设定的边界。
- 已确认首版采用纯客户端 Fabric 26.2 模组；装有该模组的客户端加入服务器后才能开启 AI 功能。服务器无需安装本项目插件。
- 第一版必须能正常使用，界面感知与菜单操作属于交付要求。
- 必须能感知服务器下发的 UI 与 BossBar 等信息，不能出现行动能力具备却无法操作现有菜单的情况。
- 模型不锁定：本地 4B、7B、API 与混合方案均可；具体选择依据任务表现和延迟评估。
- 用户确认模型在 H 盘。当前开发环境只见 C/D/E 盘，具体模型路径及运行机器在搭建时核对。
- 现有 DeluxeMenus 配置位于 `C:\Users\Administrator\Desktop\DeluxeMenus`，是用户从服务器拷贝的资料。该目录内有 10 份菜单配置与总配置，包含页面跳转、左/右键、Shift 左键、延迟打开其他插件界面等交互。
- 需要操作这些 DeluxeMenus 菜单、其他插件的箱子式 UI，以及箱子商店通过聊天栏呈现的菜单。
- 服务器已有 LuckPerms；不另建权限管理系统，普通客户端动作继续由现有服务器和插件权限判定。
- 要尽快交付，控制开发额度消耗，减少重复调研与非必要模块。
- 用户提供服务器插件目录截图，确认存在 QuickShop-Hikari 6.3.0.1、SweetPlayerMarket 1.0.16、TrChat 2.4.9、AuthMe 6.0.0、DeluxeMenus 1.14.1、LuckPerms 5.5.53 等文件。截图确认文件名，不证明实际启用状态或运行兼容性。
- 所有玩家都能下指令；本地控制优先级高于公共聊天控制。公共指令使用明确前缀，避免把日常聊天自动当作任务。
- 用户要求通过聊天中的玩家名或 @ 提名交流，回复应像正常玩家一样发到服务器聊天；保留显式任务前缀。
- 本地 4B 思考模式开启，用户选择 256 token 预算优先响应速度。
- 用户授权完成后 git commit 和 push 到 `https://github.com/zht1232/AI_mcplayer`，并要求优化 UI。
- 用户授权在桌面选择并创建交付文件夹，提供现有构建工具目录 `C:\Users\Administrator\Desktop\插件开发\构建工具`。

## 已确认架构：纯客户端 Fabric 模组

当前按用户已批准的纯客户端路线构建。下表保留此前方案比较，仅作决策背景；首版不实现桥接插件。

| 方案 | 界面与行动路径 | 主要取舍 |
|---|---|---|
| 纯客户端模组 | 真实账号登录；读取客户端菜单、HUD 与世界状态；正常客户端交互 | 能获得玩家接收到的数据，但服务器规则与第三方插件业务语义主要靠提示、配置和适配获取 |
| 客户端模组 + 辅助插件 | 保留真实账号及客户端交互；插件提供明确授权的规则与语义，并协助确认结果 | 适合现有插件服务器，需要维护客户端与插件之间的协议 |
| 纯插件 | 服务端假玩家或 NPC；需要自行实现界面感知、应答与玩家行为兼容 | 可以实现 AI 玩家，但缺少现成真实客户端来承接界面显示与输入；通用 UI 兼容需要额外工程 |

已确认部署关系：

```text
本地模型 / API
       ↕
AI 专用 Minecraft 26.2 客户端（装 AI 模组，独立账号）
       ↕ 正常游戏协议
现有 Paper 26.2 服务器（现有玩法插件）
       ↕
主人自己的游戏客户端
```

- AI 模组负责：玩家视角下的世界与 UI 感知、正常客户端动作、确定性任务执行、自主目标与任务队列、异步模型接入、记忆。
- 本项目首版不开发服务端插件，不另建权限管理系统。
- 菜单点击、挖掘、放置等日常动作建议经真实客户端执行，并观察服务器实际结果；服务器取消或纠正必须反馈给规划层。
- 模组控制安装它的客户端当前登录账号；若用户希望自己同时游玩，需要另开不同账号的客户端。
- 模型选择与游戏接入方式独立，不因切换本地模型或 API 而更换身体实现。

## UI 感知与操作要求

感知应保留可操作的结构；必要时补充图像与资源映射。数据已经收到，不代表模型已经理解业务含义。

| 界面 | 必须获取或实现的内容 |
|---|---|
| 背包、箱子、原版工作站 | 标题、类型、槽位、物品名称/Lore/组件、数量、光标物品、同步数值；执行适用的点击、移动物品、关闭等交互 |
| 箱子式插件菜单 | 在普通容器能力之上识别按钮与页面状态，支持实际菜单的左右键、翻页、返回、确认、动态刷新 |
| 原生 Dialog | 标题、正文、按钮、输入字段；保留原动作与参数，填写并提交，包含登录/配置阶段实际使用的 Dialog |
| 聊天、书本、提示文字 | 保留文本组件及适用的点击/悬停动作，支持业务需要的交互 |
| 聊天栏商店菜单 | 箱子商店插件已由截图确认为 QuickShop-Hikari 6.3.0.1；读取可点击组件与悬停说明，处理执行/建议命令及文本输入的适用流程，确认实际交易结果；实际流程需结合配置与运行验证 |
| BossBar | 读取当前存在的条目、标题、进度、颜色和样式，跟踪增加、更新、删除；原生 BossBar 本身没有按钮点击语义 |
| ActionBar、Title、侧边栏、TAB | 获取本账号收到并呈现的相关状态，避免只读取聊天文本 |
| 资源包图形、自定义字体、图标菜单 | 保留字体和资源标识，结合本服资源映射或视觉解释获取含义；需要按实际资源包验收 |
| 第三方客户端自定义 Screen | 需要核对对应模组及输入协议，不能从支持原版容器推导自动兼容 |

所有菜单动作必须校验当前界面，避免在已关闭、被替换或刷新后的旧页面执行过期点击。发出点击不能直接等同业务成功；确认依据包括菜单、物品、余额或相关状态的实际变化。

## “像人”的建议验收定义

以下是把抽象目标转成可观察行为的建议，需要继续与用户细化：

- 使用正常账号的移动、跳跃、挖掘、放置、战斗与容器交互流程，尊重服务器实际判定。
- 能持续完成有目的的生存活动，知道库存不足、工具损坏、背包满和危险会改变当前任务。
- 能解释正在做什么、为什么失败、是否需要帮助；任务结束依据目标条件确认。
- 具备稳定的身份、性格与记忆，互动方式及主动聊天频率由后续需求确定。
- 主人能停止、暂停、继续或替换任务；紧急停止直接到执行层。
- 死亡、断线、重启、传送和换维度后重新读取状态，防止旧动作继续作用于新环境；各场景的恢复行为待确认。

## 第一版交付门槛

第一版功能范围还需收敛，但“正常使用”必须由实际场景验证，不能仅由工具数量、编译成功或模型问答分数判定。

1. 在匹配现有核心、主要插件和资源包的环境登录，并能作为独立账号活动。
2. 对确认的本服菜单逐项完成打开、读取、操作、结果确认；验证动态刷新、返回与关闭等适用行为。
3. 验证本服实际使用的 BossBar、ActionBar、侧边栏、TAB 和 Dialog 等信息通道。
4. 至少完成约定的自主生存闭环，例如发现指定库存不足后采集、处理、回基地存入指定箱子；具体闭环尚未最终选定。
5. 验证任务取消、背包满、领地拒绝、死亡、断线等适用失败场景，不把失败误报为成功。
6. 在约定运行时长和场景中验证稳定性、对话与执行延迟、重复任务成功率；数字指标待实际环境与功能范围确定。

实施中应先验证本服 UI 与普通玩家动作能否贯通，再扩大自主生存能力。中间工程阶段可以有原型，第一版交付需通过上述约定门槛。

## 原实施规划需纠正的事实与推断

- “服务端没有键盘，所以不能逐 tick 控制”不成立；参考项目 Numen 与 mc_aiplayer 均有服务端玩家执行逻辑。
- Numen pathing 独立于其大脑引擎，但 Body、Physics、PlayerHands 等依赖服务端玩家；不能原样作为真实客户端控制层。
- 当前本地源码目标为 1.21.1。26.2 版本迁移与客户端身体适配是两个问题，工作量尚未验证。
- 现有 baseline_test.py 是 12 道问答的关键词命中测试，7%/56% 不是完整答案准确率，也不能证明 4B 能可靠自主玩游戏。
- ops-manual.md 是运维笔记，当前文件不能直接当作已经准备好的 2000 条问答训练集。
- 后置条件、任务取消和行动边界需要从首批动作开始设计。
